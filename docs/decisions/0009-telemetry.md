# 0009. 실제 사용자 성능 지표와 화면 오류를 우리 DB에 모으기

- 날짜: 2026-11-08
- 상태: 결정

## 배경

성능은 측정용 Chrome 한 대로 재 왔다. 그 덕분에 방침 배너 LCP 회귀(4,024ms)를 찾았지만,
가족이 실제로 쓰는 폰에서 얼마나 빠른지와 어떤 화면 오류가 나는지는 알 수 없었다.

## 결정

- `next/web-vitals`로 LCP, CLS, INP, FCP, TTFB를 모아 우리 DB(`web_vitals`)와 GA(`web_vital` 이벤트)에 함께 보낸다
  - DB: 지표별 p75를 SQL로 바로 계산한다 (GA 보고서는 백분위를 보기 어렵다)
  - GA: 화면별 분포와 다른 이벤트와의 관계를 본다
- 잡히지 않은 오류, 처리되지 않은 Promise 실패, 화면 그리기 오류(`app/error.tsx`)를 `client_errors`에 모은다
- 브라우저는 모아 두었다가 화면을 숨기거나 떠날 때 `sendBeacon`으로 한 번에 보낸다. 오류는 바로 보낸다
- 매일 오전 9시대에 운영 지표 메일(최근 24시간 p75, 많이 난 오류, 알림 문구별 열기 비율)을 보낸다

## 개인정보

- 회원 번호, IP, 브라우저 정보 문자열, 주소의 검색어(초대 코드 등)를 저장하지 않는다. 화면 이름(탭)과 기기 종류, 브라우저 이름만 남긴다
- 방침의 "자동 수집: 접속 기록, 기기와 브라우저 정보, 서비스 이용 통계" 범위 안이며, 받은 날부터 90일 뒤 지운다
- 외부 오류 수집 서비스(Sentry 등)는 쓰지 않는다. 쓰면 해외 위탁 항목을 방침에 추가해야 한다

## 받아들인 한계

- 로그인 전 화면 오류도 받아야 해서 수집 API는 로그인을 요구하지 않는다. 같은 사이트 요청만 받고, 크기와 개수, 인스턴스별 횟수를 제한한다
- 로컬 개발 서버와 테스트 기기로 표시한 기기의 성능 지표는 보내지 않는다 (오류는 보낸다)
- 오류 묶음과 소스맵 복원 같은 기능은 없다. 오류가 늘면 외부 서비스로 옮기는 것을 다시 검토한다
